▌Short answer
▌
▌CCIP is not stateless.
▌The Router itself keeps almost no state, but every token-related call that the OnRamp /
▌OffRamp executes goes through TokenAdminRegistry → getPool(), and the pool it returns
▌points to a state-heavy TokenPool contract. If you wipe or ignore that storage you break
▌token transfers.
▌
▌Contract	State that must survive	Why it matters at run-time
▌TokenAdminRegistry	s_tokenConfig[token].pool + the s_tokens list	OnRamp / OffRamp look the
▌pool up here before every lock/burn or mint/release
▌Chainlink Documentation
▌
▌TokenPool (one per token)	remote-chain selectors, remote pool addresses, rate-limiter
▌buckets, router pointer, etc.
▌Chainlink Documentation
▌	Actual lock/burn/mint/unlock happens here; wrong data ⇒ revert
▌FeeQuoter, NonceManager, …	less critical for a local test / devnet, but needed for fee maths
▌& ordering on a prod-like fork	
▌
▌So:
▌
▌You don’t have to replay every “claim admin / accept admin / setPool” tx—only the final
▌storage needs to be in place.
▌
▌The only field the live CCIP core cares about when bridging is TokenAdminRegistry.setPool
▌(plus the data inside each pool). Admin fields are permissioning only.
▌
▌If you preload that storage (via genesis alloc.storage or *_setStorageAt) all tokens work
▌“out of the box”. Skip it and the Router will still answer, but the first lock/burn call
▌from the OnRamp will revert with TokenNotConfigured/address(0).
▌
▌What this means for your fork
▌
▌Snapshot once, not every tx

> Short answer: to make “all existing CCIP tokens just work” without re-onboarding, you must
  preserve the TokenAdminRegistry’s state and every TokenPool it points to. The Router is
  mostly stateless for tokens, but keeping it (and its pointers) at the canonical address
  preserves dApp compatibility. RMN proxy, FeeQuoter, and NonceManager must either keep
  their addresses or you must update the Router’s storage to point at your versions.


  What must match addresses


  - TokenAdminRegistry: keep at the canonical address with full storage cloned (token → pool
  mapping and tokens set). Every transfer uses registry.getPool(token).
  - TokenPools (all in registry): the pool addresses the registry points to must exist with
  their code + storage (remote selectors, remote pools, rate-limits).
  - Router: keep at canonical address if you want existing dApps/SDKs to work without
  reconfig. Otherwise you must update every caller to the new Router.
  - RMN proxy: keep the same address if you copy Router storage as-is (Router stores an RMN
  pointer). Otherwise, update Router’s RMN pointer in storage.
  - FeeQuoter and NonceManager: keep addresses or update the Router’s pointers in storage.
  They are used for fee math and sequencing.


  What can be new addresses


  - OnRamp / OffRamp: you can redeploy fresh ones; just patch the Router’s per-chain tables
  (destChainSelector → onRamp, and OffRamp allow-lists). Your scripts in hardhat-ccip-
  contracts/scripts/deploy/ccip-v1_6 already do this (see 05-configure-lanes.ts).
  - Registry module owner: optional; not used at runtime for transfers (only for admin UX).
  - TokenPoolFactory: not required at runtime; only for creating new pools.
  - LINK/WETH: only required if you intend to bridge those tokens or use LINK for fees; keep
  addresses or adjust config accordingly.


  Why this is necessary


  - Router is near-stateless for “supported tokens”, but Ramps resolve the token’s pool at
  runtime via TokenAdminRegistry.getPool(token); missing/mismatched state reverts with a
  “not configured/zero address” failure.
  - The Pool contracts hold critical per-token/per-chain state (remote pool addresses,
  selectors, rate-limits). If a referenced pool is missing or has wrong storage, mint/unlock
  fails on the destination chain.

> Short answer


  - Forked envs: you can reuse the mainnet TokenAdminRegistry and all TokenPools as-is. No
  redeploy or preload needed on a live fork.
  - OnRamp/OffRamp do NOT need to be at mainnet addresses. They’re not part of token
  configuration. Router + OffRamp config just need to point to your new ramp addresses.
  - Chain selectors must match across both ends for existing CCT pools to “just work”.
  ChainSelector is independent from chainId. You can keep your dev chainId unique and still
  use the mainnet chainSelector constants.


  On your “ranges → map to one selector” idea


  - You don’t need to customize node libraries. Simply:
      - Use mainnet chainSelector values in your deployment config (they’re explicit params
  in your scripts).
      - In your node orchestration, map those chainSelectors to your dev RPCs.
  - Caveat: if two dev networks use the same selector (e.g., both “Ethereum-mainnet
  selector”), don’t connect both to the same DON. Either:
      - Run one “Ethereum” testnet per DON at a time, or
      - Isolate DONs/enclaves per environment so selectors don’t collide off-chain.


  Legend — keep vs redeploy


  - Reuse unchanged (on fork; or Preload at canonical address on fresh chain)
      - TokenAdminRegistry: keep; critical token→pool mapping. No need to own.
      - TokenPools (all registry.getPool(token) outputs): keep; include code+storage. No
  need to own.
      - Router: keep address for dApp compatibility; set owner to your EOA (impersonate/
  patch) so you can update ramp tables.
      - RMN proxy: keep if Router storage points to it (you can disable RMN checks on
  OffRamp).
      - LINK/WETH/ERC20s: keep if you bridge them or use LINK as a fee token.
  - Redeploy and own (addresses can be new)
      - OnRamp, OffRamp: your DON keys/config require this.
      - NonceManager, FeeQuoter: easier to own; or keep mainnet ones and set owners to your
  EOA.
  - Optional (admin UX only; not needed at runtime)
      - RegistryModuleOwnerCustom, TokenPoolFactory.


  Why selectors matter


  - Pools store remote chain selectors and remote pool addresses. If your dev chains use
  different selectors, you must reconfigure every pool or rewrite storage.
  - If you keep mainnet selectors (regardless of chainId), the registry/pool state stays
  valid and all CCT tokens work out of the box — provided you also run the partner chains
  with matching selectors and preload those remote pools.

  - Option B: Multiple instances per chain type → isolate DON per env; or assign new
  selectors and rewrite pool storage (heavy; requires admin or preload storage surgery).

  - You do NOT need to modify chainId to match mainnet; keep it unique to avoid replay;
  selectors can still be mainnet constants.
